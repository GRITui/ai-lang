The language an LLM can't get wrong AINL's entire grammar is 10 GBNF rules and 561 bytes. Hand it to any constrained decoder — llama.cpp, vLLM, Ollama, LM Studio — and the output is valid by construction, not by retrying.

01The proof

Two runs, each comparing the same model, same prompts, same temperature with and without the grammar applied. The check is GBNF membership — is the output in the language of the exported grammar? That is the sound detector; ainl ast is not, because the parser is a superset of the grammar and accepts invalid input.

When the model is the bottleneck

Qwen2.5-0.5B, 20 prompts, llama.cpp constrained decode — the case AINL is designed for.

When the model is strong

Qwen3.8-27B-FP8, 12 checkable tasks, scored by exact stdout match.

The second result matters more than the first.

The constraint never fails — 20/20 and 10/10, two models, two decoders. That is the guarantee.

But on a strong model it is insurance, not an improvement: both arms scored 9/10 and produced byte-identical output. The model already writes valid AINL unprompted, so there is nothing left for the grammar to rescue. Constraint value scales inversely with model capability.

What it does not buy you

It guarantees syntax, not semantics. The one miss in the 27B run is the proof. The model treated list as a two-argument constructor, so (double-each (list 1 2 3)) printed (2 (4 (6))) instead of (2 4 6). That program is syntactically perfect — it passes the grammar, it runs, and it is wrong. No grammar can fix it; it is a property of the model.

03generate → validate → compile → run

Every command below was run on the commit this page was written against, on a program a model actually wrote.

1

Generate under the grammar

Local llama.cpp, or any OpenAI-compatible gateway. The grammar is portable; the language is not in the way.

llama-cli -m model.gguf -f prompt.txt \
    --grammar-file <(ainl grammar --gbnf) -st
2

Validate — O(n)

Is the output in the grammar's language? This is the same check the published numbers are scored with.

$ python3 scripts/gen-harness/validate_gbnf.py fib-10.ainl
True
$ python3 scripts/gen-harness/validate_gbnf.py some_python.py
False

The negative control is the point: free-form Python is rejected. ainl ast would have accepted it.

3

Compile — AINL → C → native

One self-contained C file; the micro-runtime is inlined, so the binary links against nothing but libc.

$ ainl compile fib-10.ainl -o fib10
compiled fib-10.ainl -> fib10
4

Run

$ ainl run fib-10.ainl
55
$ ./fib10
55

05What didn't work

Listed because a pitch that only shows wins isn't a pitch you can trust.

+108%
Token density: the goal was not met. AINL uses ~2× the tokens of idiomatic Python, and more than JS (+64%) or Ruby (+95%). The original "token-dense, optimized for LLM context" premise is disproved. AINL's real advantage is reliability of generation, not token count.
0/20
A 0.5B model cannot write AINL. The grammar held at 100%; the outputs were byte-identical degenerate templates and none ran. Syntax was never the bottleneck — model capability was. Use a 27B-class model.
—
No semantic guarantee. Constrained decoding removes an entire class of failure (invalid syntax) and no classes of logical error. The model still has to be right.

06The rest of the language

A generation target is only useful if the output is worth keeping.

  • One unambiguous parse tree. Uniform (op arg...), no infix, no precedence, no terminators. Serialized to stable JSON with source spans and read back losslessly.
  • Lossless interop. The same AST projects to idiomatic Python, JavaScript, and Ruby — byte-equivalent across all four backends.
  • 52 builtins across the interpreter, the AOT binary, and all three transpiler targets, with byte-identical output on every one.
  • Zero external dependencies. A small static Rust binary.
(def sq (fn (x) (* x x)))
(print (sq 12))            ; 144

(def fib (fn (n)
  (if (< n 2) n
    (+ (fib (- n 1)) (fib (- n 2))))))
(print (fib 20))          ; 6765
